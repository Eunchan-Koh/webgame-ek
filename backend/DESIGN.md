# 백엔드 설계 (MVP)

## 고른 설계: 얇은 3단 구조 (라우터 / 게임 규칙 / 저장소)

```
app/
  main.py   라우터 + 시작 처리. HTTP 요청을 받아 규칙과 저장소를 이어 붙이고 응답 모양을 만든다.
  game.py   게임 규칙. 아이템 배치, 클릭 판정, 시간 계산, 점수 계산, 시간 초과 처리.
            순수 함수만 둔다 (DB·Redis·HTTP를 모른다. 현재 시각도 인자로 받는다).
  store.py  Redis: 진행 중인 게임 상태 읽기/쓰기 (TTL, 동시 클릭 대비 낙관적 잠금).
  db.py     PostgreSQL: 테이블 생성, 아이템 시드, 아이템 목록 조회, 끝난 판 기록 저장.
tests/
  test_game.py  game.py 규칙 테스트 (점수, 판정, 시간 초과).
```

의존 방향은 `main -> game, store, db` 하나뿐이다. `game.py`는 아무것도 import하지 않는다(표준 라이브러리만).

### 이유

- **서버 정답 판정·점수가 이 게임의 핵심 규칙이다.** 이 규칙을 I/O 없는 순수 함수로 떼어 두면
  시각을 인자로 넣어 "599초 시점 클릭", "600초 지난 클릭" 같은 경우를 DB·Redis 없이 바로 테스트할 수 있다.
  시간을 서버 기준으로 재야 하므로 시간 계산을 한 곳(game.py)에만 둔다.
- **MVP를 일주일 안에 만든다.** 파일 4개면 전체 흐름이 한눈에 보이고, 프론트와 맞물려 빨리 확인할 수 있다.
- **이후 계정·랭킹이 붙는다.** 그때 `db.py`에 유저 테이블과 쿼리, `store.py`에 랭킹(Redis sorted set)·세션을
  더하고, 라우터가 커지면 `main.py`의 라우트를 기능별 파일(`routes/games.py`, `routes/auth.py`)로 나누면 된다.
  게임 규칙(`game.py`)은 그대로 둔 채 붙일 수 있다. 지금 그 파일들을 미리 만들지는 않는다.

### 저장 위치

- Redis `game:<game_id>`: 진행 중 게임 상태(JSON). 생성 시 TTL 1시간. 끝난 뒤에도 TTL이 남은 동안 조회 가능.
  - 같은 게임에 클릭이 동시에 와도 찾은 아이템이 덮어써지지 않도록 `WATCH`/`MULTI`로 읽고-고치고-쓰기를 한다.
    "끝남"으로 바뀌는 쓰기에 성공한 요청 하나만 PostgreSQL에 기록하므로 결과가 두 번 저장되지 않는다.
- PostgreSQL
  - `items(id, slug, name, image)`: 아이템 풀. 시작 시 비어 있으면 8개 시드.
  - `game_results(game_id, score, found_count, started_at, ended_at)`: 끝난 판 한 줄.
  - 마이그레이션 도구 없이 시작 시 `CREATE TABLE IF NOT EXISTS`.

### 시간 규칙

- 시각은 서버의 `time.time()`(초, 실수). 게임 생성 시 `started_at`을 저장한다.
- `remaining_sec = max(0, floor(started_at + 600 - now))`.
- `now >= started_at + 600`이면 시간 초과. 이때 점수는 `100 * 찾은 개수`, 종료 시각은 `started_at + 600`.
- 5개 다 찾으면 그 클릭 시점의 `remaining_sec`로 `100 * 5 + remaining_sec`.
- 시간 초과는 별도 타이머 없이, 그 게임에 요청(조회·클릭)이 올 때 확인해서 처리한다.

## 검토했지만 고르지 않은 대안

- **파일 하나(main.py)에 전부**: 처음엔 가장 빠르지만 판정·점수 규칙이 Redis/HTTP 코드와 섞여
  시간 경계 테스트가 어려워지고, 계정·랭킹을 붙일 때 파일을 다시 쪼개야 한다.
- **클린/헥사고날 아키텍처(저장소 인터페이스, 서비스 계층, DI 컨테이너)**: 저장소 구현이 각각 하나뿐인데
  인터페이스를 두면 코드만 늘어난다. 일주일 MVP에 과하다.
- **SQLAlchemy ORM + Alembic**: 테이블 2개, 쿼리 3개라 ORM·마이그레이션 도구의 이점이 없다.
  계정 기능으로 테이블이 늘고 스키마 변경이 잦아지면 그때 검토한다.
- **게임 상태를 PostgreSQL에만 저장**: 진행 중 상태는 클릭마다 바뀌고 오래 보관할 필요가 없어 Redis+TTL이 맞다
  (기술 스택 결정과도 같다).
- **비동기(async) DB·Redis 클라이언트**: FastAPI의 동기 엔드포인트(스레드풀)로 MVP 트래픽에 충분하고 코드가 단순하다.
- **시간 초과 시 백그라운드 작업으로 자동 종료**: 워커·스케줄러가 더 필요하다. 요청 시점 확인으로 계약
  ("조회 시 시간이 다 됐으면 끝난 상태로 반환")을 만족한다.
